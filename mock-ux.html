Written Screen Explanations (one paragraph each)

1. Dashboard. The landing screen balances Monitor and Explore modes. A support engineer arriving mid-shift does a 90-second health check before diving in: they can pick the affected client immediately (the primary action), glance at indexing health via the three KPI cards, and either resume a recent search or jump to any client. Because the PRD frames the product as account-first, this screen's first act is choosing which account — establishing the retrieval boundary before any search happens.

2. Clients. This screen turns "select the affected client" (user story #1, FR-01) into a concrete, searchable step. Every row exposes the client ID, document count, and live indexing status so the support engineer can trust the knowledge base before opening it (FR-13). The pink "Open knowledge" action on each row is the single most important click on this screen — one click lands the user in the core search workflow.

3. Client Knowledge / Procedure Search. The heart of the product's Investigate and Filter modes. A natural-language query field sits at the top; the selected client is shown as a locked, visible filter so the account isolation rule (FR-06/FR-07) is transparent. Results are evidence cards showing relevance score plus exact source metadata (document, page, section) — so a support engineer can judge correctness before opening, and every card is a drill-down entry into Source Detail. This is where "reduce time and ambiguity" is actually delivered.

4. Document Library. Serves the Support Lead's trust need ("see account-specific documents and their indexing status"). It lists every approved document for a client with type, version, and a colored indexing-status indicator. Failed or re-indexing items are colored and actionable. This screen is the "source of truth" that makes the rest of the product trustworthy — it answers the PRD quality question of whether the knowledge base is complete and current.

5. Document Upload & Indexing. The Knowledge Administrator workflow satisfying FR-12/FR-13. Because every document must be account-bound (FR-02), client selection is the first mandatory field. The form captures document type and optional version/date metadata, then runs the visible processing pipeline (extraction → cleaning → chunking → embedding → indexing → validation). A success state confirms indexing with a chunk count; validation errors are shown inline rather than as a blank failure.

6. Result / Source Detail. The verification screen for Investigate mode — where the PRD's accuracy and traceability requirements come alive. It shows the grounded RAG answer (clearly distinct from evidence), the exact source metadata, and the matched passage highlighted, so a support engineer can confirm the procedure before acting. Critically, it hosts the insufficient-evidence state: instead of fabricating a procedure (FR-11), the system states it could not verify the answer and offers next actions.

Design Reasoning & PRD Feature-Placement Justification

Non-obvious layout decisions

  • Persistent left sidebar on every screen — supports Explore mode's non-linear navigation. Users jump between Clients, Search, and Library without losing context, while a top client-scope indicator keeps the account boundary visible.
  • Client picker on the Dashboard as the primary CTA. Support engineers start every incident by narrowing to the affected account; placing that as the first, pink action matches their actual morning/daily arc and enforces account isolation before search.
  • KPI cards on Dashboard but NOT screens 2–6. KPIs are only meaningful where the user judges system health (Monitor mode). On the core search screen, the "KPI" is the query box and the results, so cards would be decoration-first clutter.
  • Relevance % + source metadata inline on every result card. This is the decision context a support engineer needs (traceability, FR-10) — surfaced at the point of decision rather than hidden behind a click.
  • Source Detail split into "Grounded answer" vs "Matched passage." The PRD demands users "distinguish retrieved evidence from generated explanation" — so answer and evidence are visually separated, never merged.
  • Filters (2) + Search CTA are separate, labelled elements. Per the checklist, filters expose what they filter, auto-apply behavior, and a Clear button. The Search button is the primary pink action.
  • Error/empty states are inline, never blank. Every failure (no results, connection, upload validation, permission, insufficient evidence) has a message, a reason, and an action — matching Section 2's "never show a blank screen."

Mock UX Acceptance Checklist (7 questions)

  1. ✓ Understandable without verbal explanation: every grey box and pink action carries a label (component purpose / behavior). Source Detail, filters, and states are self-describing.
  2. ✓ KPI metrics above the fold: Dashboard has 3 KPI cards immediately under the header; nothing scrolls to see indexing health.
  3. ✓ Filters labelled with interaction model: Search & Clients show what they filter, auto-apply, and a Clear button; the Search CTA is explicit.
  4. ✓ Navigation understandable, ≤2 clicks: Dashboard → client → Search (2 clicks); Drill-down → Source Detail (1 more). Sidebar reaches every screen.
  5. ✓ Error + empty states represented: no-results, empty client, connection failure, upload validation, permission, insufficient-evidence — all shown with actions.
  6. ✓ Insights readable (decision from each chart/result): each result card is annotated with what it answers and its evidence; no decorative charts on the core screens.
  7. ✓ Solves the PRD problem: support engineer → select client → natural-language search → verify grounded source → act. Fewest steps (2–3 clicks) for the primary incident workflow.
